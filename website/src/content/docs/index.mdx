## One grammar, many projections

polytype lowers Go types, statically at `go generate` time, into one closed
type grammar and projects it into whatever the boundary needs:

| Projection | How |
| --- | --- |
| JSON Schema, embedded in Go, for LLM tool calls and structured output | `go tool polytype` (always on) |
| `ValidateJSON` methods | `--validate` |
| Go JSON codecs: membership-checked enums and discriminated sealed unions | Inferred from the types; no flag |
| Structural TypeScript declarations | `--typescript DIR`, or the `typescript` package |
| devalue transport: Go runtime port plus generated typed codecs | `devalue`, `devalue/codegen` packages |
| Your own backend | `grammar`, `typegrammar` packages |

## What every projection guarantees

- The Go type is the single source of truth; nothing uses runtime reflection.
- Property order follows Go struct field order, producing deterministic prompts and stable wire layouts.
- Unknown properties are rejected: `additionalProperties: false` in schemas, strict decoders elsewhere.
- Go doc comments become LLM-facing schema descriptions.
- Ordinary and nullable fields are required; only `Optional[T]` removes a property from `required`.
- Union discriminators and enum values are the same in every projection.
- A shape that cannot be represented faithfully fails generation with a diagnostic naming the type or field, instead of widening to `any`.
- Generated files are safe to commit and verify in CI.

Need exact exported signatures? The generated [Go API reference](/api/) is available,
but most integrations should begin with [Getting started](/getting-started/).
