# Material findings

Resolution (2026-09-06): the manager accepted 1, 2, 3 and 5 and rejected 4.
All four accepted findings are fixed, with tests; finding 1's stated
consequence ("cannot compile") is itself wrong — a tagless switch admits
duplicate boolean cases — though its remedy stands. See the "Review resolution
pass" section of `ephemeral/worklog/202609061434-issues-104-107.md`.

1. **Issue — value-mode enum aliases make generated devalue codecs fail to compile.** The exported grammar deliberately admits duplicate underlying values in value mode (`typegrammar/validate.go:396-419`), and the existing generator contract explicitly tests that such aliases are supported (`internal/builder/enum_codec_test.go:35-68`). The devalue encoder and decoder nevertheless emit one `switch` case per member without deduplicating wire values (`devalue/codegen/encode.go:96-110`, `devalue/codegen/decode.go:166-188`). For an admitted enum such as `Red = 1; Crimson = 1`, both generated switches contain duplicate cases, so the output cannot compile. The “covers every node kind” fixture uses only distinct enum members and does not exercise this supported shape.

2. **Issue — integer enum members beyond 2^53 are rejected instead of following the brief’s lossy-number decision.** The brief settles that every Go numeric kind uses a JavaScript number and values beyond 2^53 lose precision (`ephemeral/devalue-projection/design-brief.md:151-155`). Scalar fields follow that rule, but `enumWireLiteral` returns an error whenever an integer member is not exactly representable as `float64` (`devalue/codegen/encode.go:249-260`). Thus `Generate` rejects a valid `int64`/`uint64` enum member such as `9007199254740993`, contradicting the chosen wire mapping rather than emitting its documented lossy number.

3. **Issue — issue #107’s required beyond-2^53 recording case is absent.** Issue #107 requires the recorder’s numeric cases to cover every Go numeric kind and specifically calls out `int64`/`uint64` beyond 2^53 after #105 decides between number and BigInt. The decision was “number, with precision loss,” but the recorder’s largest integer is only the exactly-safe `9007199254740991` (`devalue/testdata/record/main.go:29-36`); the generated golden consequently never records the boundary behavior the issue singled out. Regeneration is reproducible, but this acceptance item is not demonstrated.

4. **Issue — the seeded fuzz target weakens the brief’s required byte-identity property.** The brief requires `FuzzRoundTrip`, seeded from the recorded entries, to hold the same `Stringify(Parse(bytes)) == bytes` property as the golden test (`ephemeral/devalue-projection/design-brief.md:217-220`). The implementation explicitly declines byte equality for fuzz inputs and checks only that serialization reaches a fixed point after canonicalization (`devalue/golden_test.go:58-88`). The 5-second fuzz run passes, but it therefore does not demonstrate the acceptance property the brief names.

5. **Issue — valid same-package type names can collide into duplicate generated functions.** `safeIdentifier` maps a Unicode name such as `雪` to `_u96EA_`, which is also a valid literal Go type name (`devalue/codegen/names.go:24-37`). `allocateNames` detects the shared base but disambiguates both definitions only with their package path (`devalue/codegen/generate.go:132-149`); when both types are in the same package, both still receive the identical base and `g.claim` does not alter either one. `Generate` then emits duplicate `Encode_u96EA_`/`Decode_u96EA_` families. This is not hypothetical machinery: the branch’s TypeScript compiler test uses exactly the `雪` plus `_u96EA_` collision as an admitted projection edge case (`internal/typescript/tsc_test.go:20-49`), but the new devalue backend has no equivalent protection.
