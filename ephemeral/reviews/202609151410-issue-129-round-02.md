## Findings

### 1. [issue] Programmatic generation still parses and can fail on source `SealedUnion` markers

Issue #129 requires `codegen.Gen` with programmatic configuration to succeed
"regardless of which `polytype.*` markers exist in the target package." The
implementation still makes one marker an exception. In configured mode,
`internal/syntax/scan_result.go:430-435` skips every source call *except*
`SealedUnion`; lines 475-477 then run the build-tagged-source parser before
`internal/builder/programmatic.go:74-91` can apply the executable configuration.
That parser rejects non-built-in inflectors at
`internal/syntax/sealed_union_decl.go:52-57` and duplicate source declarations
at lines 60-61.

This makes a documented executable configuration fail merely because it lives
in the target package. For example, an ordinary production file may validly
export:

```go
var Config = polytype.Compose(
	polytype.Declare[Tree](),
	polytype.SealedUnion[Node]("kind", strings.ToLower),
)
```

`sealed_union.go:12-22` explicitly permits any non-nil `func(string) string` in
executable codegen configuration. A generator importing and passing `Config`
to `codegen.Gen` nevertheless scans the same source call as though it were a
build-tagged marker and fails with "build-tagged declarations require
polytype.Snake, polytype.Camel, or polytype.Pascal." Two otherwise valid source
configuration values for the same union likewise fail as duplicate markers
before the passed runtime configuration can override either. The added test at
`internal/builder/declaration_file_test.go:224-241` codifies the exception
instead of covering the acceptance criterion.

Configured generation must take union settings from its passed configuration,
just as it now takes roots from that configuration. Source-only union settings
needed by declaration-file generation can remain in declaration mode; they
must not make `codegen.Gen` depend on or fail from target-package marker calls.

### 2. [issue] The CLI still interprets direct executable configuration values in ordinary Go files as declaration-file markers

The current uncommitted fix correctly stops rejecting an ordinary top-level
`Compose` call, but it tests whether the source file is a production file only
inside the `default` switch branch at
`internal/syntax/scan_result.go:480-496`. Recognized calls take earlier branches:
`Declare` at lines 462-473 and `SealedUnion` at lines 475-477. Consequently,
ordinary executable values such as:

```go
var Config = polytype.Declare[InternalModel]()
```

are still silently added to a CLI run's roots. A direct ordinary
`SealedUnion` value is likewise applied to the CLI even when it was intended
only for a separately invoked generator configuration. This contradicts the
new distinction stated by the code comment at lines 486-490 (only a
generation-only declaration file is read as declarations), the README's
separation between programmatic values and `schema.go`, and the public fact
that `Declare` and `SealedUnion` return executable configuration values.

The practical failure is not cosmetic: if `InternalModel` uses a shape valid
for its separate backend but outside the CLI's selected projection, an
otherwise valid declaration-file run now fails on or emits output for a root
that the declaration file never selected. The new regression at
`internal/builder/declaration_file_test.go:83-94` covers only a `Compose`
wrapper, whose outer function happens to reach `default`; it does not cover the
direct single-declaration form documented at `README.md:130-149`.

Determine declaration-file eligibility before dispatching *any* recognized
call. Production configuration values should be ignored consistently; the
generation-only file should retain the source-positioned rejection for
`Compose` and continue to process its individual markers.
