## Verified sound (no finding)

- Line counts (1,511 / 1,042), the shasum, and both baseline test claims.
- The five helpers named for reuse (`asFloat`, `formatNumber`,
  `maxArrayIndex`, `isArrayIndexString`, `propertyOrder`) are identical in
  body between the two repositories. `ptrKey` and `dateKey` are the only
  package-level name collisions and the plan addresses them.
- The flat boundary already holds with zero code change: `Stringify` of `URL`,
  `URLSearchParams`, `Temporal`, `*TypedArray`, `*DataView` returns
  `Cannot stringify arbitrary non-POJOs (<type>)`.
- skgo consumers use only `Uneval`, `UnevalWith`, `QuoteString`, `Replacer`
  plus symbols Polytype already exports. "Import rewrite, no adapter" is
  achievable.
- The malformed-string decision is correct. goja rejects the raw WTF-8
  fixtures' output with `SyntaxError: Invalid UTF-8 character`, so those five
  fixtures prove nothing today; Polytype's writer emits U+FFFD, which is valid
  JavaScript, and for valid UTF-8 the two writers are equivalent to upstream
  `stringify_string` (`utils.js:58-101`). No further machinery is warranted.
- A `feat` commit against `.releaserc.json` yields a minor release; the
  release job is gated on `vars.SEMANTIC_RELEASE_ENABLED`, and the plan already
  verifies the release after merge.

## Findings

### 1. Issue — incomplete requirement: the pinned-upstream check has no committed mechanism and is missing from the completion criteria

Missed instruction: `issue-154.md:24` "Check behavior against pinned upstream
devalue source" and `:33` "Migrate serializer fixtures checked against pinned
upstream behavior".

Evidence:

- `plan.md:175-191` says to compare output to the pinned implementation, then
  makes the only automated route conditional and prefers "a manual,
  reviewable set". `plan.md:246-247` reduces it to "any … comparison added by
  the implementation". `plan.md:258-271` (completion criteria) does not
  mention upstream at all. As written, the plan can be declared complete with
  no check against 5.9.2.
- The fixtures' stated provenance is not the pin. skgo
  `uneval_test.go:10-14` says the expected JS was copied from
  `ephemeral/inspiration/reference/devalue/test/index.test.js`. That path does
  not exist at the source commit and records no version. The 5.9.2 tarball
  ships `src/`, `types/`, `index.js` only — no `test/index.test.js`. So
  `plan.md:177-180` ("use the existing npm pin rather than a floating
  checkout" and "retain the exact upstream test … location") cannot both be
  satisfied by carrying the fixtures over unchanged; their authority is a
  floating checkout of unknown version.

Impact: the one acceptance bullet that distinguishes "ported" from "verified"
is left to implementer discretion, and the fixture header would carry a false
provenance claim into Polytype.

Smallest fix (demonstrated, not hypothetical): `devalue/testdata/record/record.mjs`
already imports the pinned package. Import `uneval` beside `stringify` and
record one more field (or a sibling file, so `golden.json` bytes are
untouched). The Go test is `Parse(case.devalue)` → `Uneval` → compare — no
second fixture model, no Node at `go test` time, and it directly proves the
plan's "one tree can be handed to either serializer" claim. Caveat the plan
must state: the 321 recorded values produce **zero** IIFE outputs and zero
sparse arrays, so a handful of cyclic/shared/sparse expressions must be added
to the recorder's generator (the flat format carries them, so they round-trip
through `Parse`; my 19-case probe did exactly this). Expression-only types
(typed arrays, DataView, URL, URLSearchParams, Temporal) cannot take this
route and remain hand-copied; say so, and correct the fixture header to cite
the pin. Then add one completion criterion naming the check. This is a
two-line extension of an existing mechanism, consistent with `AGENTS.md`
("Do not add … ledgers, or provenance machinery").

### 2. Issue — incorrect premise: the skip accounting the plan preserves is stale; 13 of 24 skips are not engine gaps

Misunderstood requirement: `issue-154.md:36-38` "Evaluate emitted JavaScript …
Explicitly account for unsupported engine features and existing skipped
fixtures."

Evidence:

- `plan.md:52-54` accepts as starting evidence that the suite "accounts for
  engine features goja lacks"; `plan.md:171` says to keep unsupported-engine
  skips "named and counted"; slice 3 says "audit every skip" with no criterion.
- Reproduction, goja at the exact version skgo pins: `typeof 1n` → `bigint`;
  `Object(1n) instanceof BigInt` → `true`;
  `new BigInt64Array([1n,-2n,3n])[1] === -2n` → `true`. Six fixtures are
  skipped as "goja has no BigInt" (skgo `uneval_test.go:144, 163, 200-205,
  344-346, 408-411`). All six are executable today.
- Under the plan's own string decision the five lone-surrogate fixtures
  (`uneval_test.go:287-292`) emit U+FFFD and become executable; they stop being
  "excluded" and need new expectations, not just accounting.
- "Custom type" and "Function wrapped in custom type"
  (`uneval_test.go:466-499`) skip because `Foo`/`Bar`/`FunctionRef` are
  undefined, yet `eval_test.go:258-266` already pre-defines `app.decode` for
  the same purpose. "Custom type" is the only fixture that exercises a
  replacer result being hoisted for shared identity, so it is the one
  replacer case most worth executing.
- Only 11 skips are genuine (`URL`, `URLSearchParams`, nine `Temporal`). The
  tripwire `evaluated < 80` (`eval_test.go:63-67`) and its comment "24 of which
  need engine features goja lacks" would be migrated as false statements.

Impact: BigInt primitives, boxed BigInt, and both BigInt typed arrays would
ship with snapshot-only proof while the plan's criteria read as satisfied.

Fix: state the audit rule — a skip survives only if evaluating the expression
in the pinned goja fails on a named missing global — unskip the rest with a
`validate` check each, and raise the lower bound to the real executed count.

### 4. Nitpick — shared value model: `Map`/`Set` identity ignores the new representations

`plan.md:88-98` keeps `identityKey` flat-only while `plan.md:126-128` promises
one tree for either serializer. Reproduced at the source commit:

```
NewSet(u8, u8).Len()            == 2
  Uneval → (function(a){a=new Uint8Array([1,2]);return new Set([a,a])}({}))   // JS size 1
m := NewMap(URL("https://a/"), 1); m.Set(URL("https://a/"), 2)
  m.Len() == 2; m.Get(URL("https://a/")) → not found
```

This is existing skgo behaviour, no known consumer keys a Map or Set on these
types, and the emitted JavaScript still evaluates, so it does not block. It
becomes a same-package inconsistency once Polytype owns both. Either add the
five types to `identityKey` (pointer types by pointer, value types by value —
`Stringify` still rejects them in `serialize`, so the flat wire is not
widened) or document the limitation on `Map`/`Set`. Implementer to verify.

### 5. Nitpick — rejection path differs from upstream for keys containing `<`, U+2028, U+2029

Upstream builds paths with `stringify_key` = `'[' + JSON.stringify(key) + ']'`
(`utils.js:121-124`); skgo `uneval.go:263-264` uses `quoteJS`. Reproduced:
key `a<b` yields path `["a<b"]` where upstream yields `["a<b"]`.
`plan.md:209` ("route all JavaScript string literals through the one shared
writer") would cement it. Diagnostic text only. Either mark it as a deliberate
difference where the plan asks for that distinction (`plan.md:185-186`) or
quote path keys JSON-style.
