## Milestone 1 (#106), step 1: type-level enum codec emission

decision: the generated `MarshalJSON` writes a per-member literal (`return []byte("4"), nil`) rather than converting the receiver and delegating to `json.Marshal`. Delegating would recurse through the new method for string enums and needs a kind-specific conversion for integers; the literal is computed at generation time from the same `constant.Value` the schema uses, so schema and codec cannot drift.
decision: members are deduplicated by wire value, first constant name wins. Two constants with the same value are legal Go and already exercised by `TestNonAdaptedEnumsAllowAliasValues`; emitting both would be a duplicate case and would not compile.
decision: a marked type whose underlying type is neither string nor integer (or whose constants do not evaluate to that kind) gets no codec at all instead of a generation error. That shape is rejected today only when a schema actually reaches the type, and this step must not turn it into a hard failure.
friction: `AssertGoldenFile` calls `t.Fatalf` inside a parallel subtest, so the first golden mismatch panics the whole `TestBasic` run and hides the rest. Regenerating the four affected goldens took one run each. It also leaves `testfixtures/asref_collision_*` temp dirs behind because cleanups do not run.
note: no production Go declares `MarshalJSON` on an enum-marked type in the repo's fixtures, so the collision case is untested. Guarding it (the `FindProductionJSONMethods` path already used for adapted enums) belongs to a later step of this milestone if it is wanted at all.
review_finding: generated enum `UnmarshalJSON` decodes into a scalar before membership checking, so JSON null is accepted whenever zero is a declared member; reject null explicitly before scalar decoding.
review_finding: type-level enum codec emission does not audit existing production JSON methods, so generation succeeds but the package then fails with duplicate method declarations; reuse the pre-write collision machinery.

### Review resolution (both findings confirmed, milestone commit amended)

decision: null is rejected by decoding the wire value through a `*underlying`
pointer rather than by a `bytes.Equal(bytes.TrimSpace(data), "null")` helper.
The helper the owner codecs use (`__jsonschema__isJSONNull`) is emitted only
under `HaveEnumCodecs && GeneratesJSONUnmarshalers`, so type-level codecs
would have had to widen that import/emission condition; the pointer target
needs nothing new, and `encoding/json` handles surrounding whitespace.
decision: a production `MarshalJSON`/`UnmarshalJSON` on an enum-marked type is
a pre-write error, not a silent skip of codec emission. It matches
`validateOwnerCodecMethods` (the same `syntax.FindProductionJSONMethods` pass
and the same error shape), and silently skipping would leave the enum without
the membership guarantee the milestone exists to provide, with nothing said.
The check only fires for markers that would actually receive a codec, so a
marked type with an unencodable underlying kind keeps its handwritten methods.
proof: the null fix is proven by behavior, not by generated text.
`internal/builder/testfixtures/enums` gained `ZeroValueEnum` (member `""`) and
`ZeroCodeEnum` (member `0`) plus `enum_codec_test.go`; `TestBasic`'s
test3-enums case runs the fixture module's own tests after generation.
Verified the test bites by deleting the emitted null guard from the generated
file and re-running (the decode then nil-derefs).
note: the earlier "no production Go declares MarshalJSON on an enum-marked
type in the repo's fixtures, so the collision case is untested" gap is closed
by `TestEnumMarkerRejectsProductionJSONMethodsBeforeWriting`.
friction: the golden regeneration friction recorded above repeated once per
template edit - four goldens, one run each, and the first `t.Fatalf` still
aborts the whole parallel `TestBasic`.

### Step: prove the owner codec and the type-level enum codec coexist (#106)

decision: no new fixture. `v1_enums_stringmode` already has the exact shape the
brief asks about - `Paint.C` in string mode via `WithStringerEnum`, `Paint.Numeric`
the same `Color` left numeric - so the coexistence test is one function appended
to that fixture's `codec_test.go`.
proof that the two codecs do not collide, found by reading the golden rather than
assumed: the owner `Paint.MarshalJSON` builds a `Wrapper` whose `json.RawMessage`
fields shadow the aliased struct's `C`/`Optional`/`Nullable`/`Remote`, so the
type-level `Color.MarshalJSON` is never reached for those fields, while `Numeric`
is left on the alias and therefore does go through it. That is why one document
carries `"c":"ColorBlue"` and `"numeric":-2` at the same time.
decision: the two non-member assertions are deliberately asymmetric. The numeric
path asserts the type-level codec's text (`99 is not a declared member of enum
Color`); the string-mode path asserts the owner codec's existing text
(`undeclared value for string-mode enum Color`), which names the type but not the
value. The step forbids changing the owner path, so the test records what it
produces.
proof: no generator or template change needed and no golden churn - the
type-level codec was already emitted, which is the outcome the step predicted.
Gates: `go test ./internal/builder/... -run TestBasic`, `go test ./...`,
`go vet ./...`, `just build-tagged`.

### Step: regeneration test, spec row, enum-guide sentence, close #106

correction (mechanism): the step and the brief both say the generated enum
codecs are safe on regeneration because they live in a `!jsonschema` file and
the scanner loads with the `jsonschema` tag. That is not the mechanism. The

the outcome, not the reason.
