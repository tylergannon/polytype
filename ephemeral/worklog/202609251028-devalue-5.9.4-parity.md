discovery (security, pre-existing in v1.1.x): `walk` treated `*Boxed` as a leaf,
so a boxed BigInt's digits were never validated. `Parse` of
`[["Object",1],["BigInt","(globalThis.pwned=3),1"]]` followed by `Uneval`
returned `Object((globalThis.pwned=3),1n)` on `3d70c98` (checked in a scratch
copy of HEAD). Porting 5.9.3's "boxed String/BigInt walk their primitive" routes
the digits through `validBigInt`, so this now fails with
`Cannot stringify arbitrary non-POJOs`. Regression cases added to
`TestUnevalRejectsExecutableFlatMetadata` and `TestUnevalErrors`. Only the boxed
BigInt path was open: `Parse` refuses to box anything but a primitive or BigInt slot.

decision: the primitive hoisting threshold measures lengths in UTF-16 code units
(`utf16Len`), as JavaScript's `.length` does. It can only turn a hoist down for a
BigInt: any counted string has a literal of at least 130 units, which always
clears it. The discriminating corpus case is `repeated_string_multibyte_127`
(127 × U+96EA: 381 UTF-8 bytes, 127 code units, so JS leaves it inline).

decision: upstream tests that need a JavaScript array of length 2^32-1, a
prototype, or non-index array properties have no Go form (a `[]any` materializes
every slot and has no prototype); they are not ported. The allocation regression
is ported with 2 arrays of 1,000,000 instead of 2,500, and the invalid-element
path with index 99,999 instead of 99,999,999.

friction: the Write/Edit tools decode `\uXXXX` escapes in their input, so raw
U+2028/U+2029 and an emoji landed in Go and JS source. -> write escape-bearing
source with a script (python) and grep for non-ASCII afterwards.
